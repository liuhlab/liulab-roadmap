# 用 Claude Code 写这个网站

这个网站的每一页，包括你正在看的这一页，都是 Claude Code 起草、再由人改出来的。值得写一写，倒不是因为这个网站本身有什么稀奇，而是这套分工很容易照搬到你自己手头的项目上。

## 各自干什么

行得通的分工是：什么值得说、说得对不对，你来定；搭建的部分交给它。

这个网站里，一个页面的起点通常是几条要点加一些观点。Claude 把它变成初稿，中英文一起写，把页面接进导航，跑一遍构建，顺手修掉自己弄坏的地方。然后停下来，等让人来评价：这个说法站得住吗？这段话读起来像人写的吗？

可以把它想象成这样一个合作者：手快，从不嫌杂活烦，但有时候分不清什么重要。它交出来的每一样东西，都只是一份提案。

## 怎么把它接进项目

有几个习惯，决定了你得到的是一个真顶事的 agent，还是一个只会生产"看着像模像样"的烂摊子的 agent。

把整个项目交给它，而不是粘贴片段。它会自己打开文件、检索、执行命令、读输出、再试一次。在聊天窗口里来回粘代码，等于把它大部分本事都扔掉了。

规矩写下来一次就好。每次会话都从零开始，上周刚讲好的事，这周它可能就换个做法。这个仓库根目录有个 `CLAUDE.md`，agent 每次会话开始都会读它，里面放的就是那些不写下来就得反复交代的东西：中英文一起写、一个页面要能一口气读完、哪种腔调不能有。它大概一百行，是整个项目里性价比最高的一个文件。

顺便说说这份"记忆"是怎么回事。agent 自己其实什么都记不住，所谓记忆，就是每次会话开始时把那份文件重新读一遍，Claude Code 读 `CLAUDE.md`，Kimi Code 读 `AGENTS.md`。所以每次纠正它，都可以让它顺手把规矩写进文件，下次会话就生效。再进一步，真正常用的固定流程，比如实验室里反复做的某类分析，可以打包成 Skill：一个写好操作步骤的文件夹，agent 只在用得上的时候才加载。实验室自己的 Skills 见[常规实验室支持](../../5-lab-code/5.1-routine-support.md)。

让它自己验收。只要它能跑构建、能看到报错，它就会先改好再拿给你；做不到的话，你就成了那条报错信息。

## 一个让人觉得很值的例子

我们想给术语加悬停释义，就是鼠标停在词上，旁边会浮出一个小气泡，写着这个词的一句话解释。这样读者第一次碰到"反向传播"这种词，不用离开页面就能看懂。结果发现常规做法在中文上根本不管用。

搁在以前，这种需求多半就搁置了。问题本身不大：现成的插件不认中文，得自己写段代码接管这件事。难的是成本，从正经活里抽出半天，去摸一个只用一次的接口，换来的还只是个锦上添花的功能，怎么算都不值。Claude Code 改变的就是这笔账：把需求讲清楚，它自己去查文档、写代码、调试，一次会话就做完了，现在全站每一页都有。

比起让它写文字，这才是 agent 更划算的地方。那些原本"不值得为它打断手里活"的小改进，现在便宜到随手就能做掉，项目于是慢慢变好，而这种变好本来不会发生。

## 哪些地方指望不上它

品味、框架、事实，这三样最终都得靠人来判断。这里第一个正经页面在所有事实都核对无误之后，光语气就又改了两轮。而且它说错话时的笃定程度，和说对话时一模一样，所以审阅这一步没法省。剩下的活儿，大半就是审阅。

## 想在自己的项目上试试

有几点是我们摸出来的。从一个已经存在的代码库开始，比从空目录开始顺；让它改之前，先让它讲讲这些代码在干什么。同一句话说到第二遍，它就进 CLAUDE.md。改动没读过之前，不留下。

想看看"一百行攒下来的偏好"长什么样，这个网站的规则文件在 [AGENTS.md](https://github.com/liuhlab/liulab-roadmap/blob/main/AGENTS.md)。
