    Linux, Git & GitHub Basics¶

    The command line, git, and GitHub are the foundation of the lab's daily workflow: typed commands drive the computing on our servers, git records every change, and GitHub shares that history with other people. Sharpening these tools pays for itself; together with Python they are what all our computing and analysis runs on, and Python gets its own page in Python Basics. These three are also the skills a coding agent leans on hardest, so the point of learning them has shifted: not memorizing commands, but reading what the agent did and judging whether it was necessary. This page starts with the operating-system and computing-environment background, then picks out the basics worth learning, a few entry-level resources, and a few places to check whether the material actually stuck.

    Operating systems: one Unix family, and Windows¶

    An operating system (OS) is the first program that starts when a machine boots, in charge of the hardware, the files, and every other program; the desktop you see is only its outermost skin. The three common desktop systems look like three, but they are two families. Unix was born at Bell Labs in 1969, and two of its descendants are with us: Linux, the free and open-source kernel Linus Torvalds rewrote in 1991, which now runs nearly every server, supercomputer, and Android phone, and macOS, whose Darwin kernel descends from BSD Unix and carries a proper UNIX trademark certification. Windows comes from a different bloodline, MS-DOS by way of Windows NT, and it differs from the Unix family in how paths are written (C:\ versus /), in command vocabulary, and in design philosophy.

    This family tree decides your daily experience. Open a terminal on a Mac and you are in Unix: the commands, paths, and toolchain are nearly identical to a Linux server's, so what you practice on your laptop works unchanged on the server. The cmd and PowerShell that ship with Windows speak another language, and most commands from a bioinformatics tutorial will not run there. The good news is WSL (Windows Subsystem for Linux), Microsoft's official way to install a real Ubuntu inside Windows: open PowerShell as administrator and run wsl --install. And since the lab's heavy computing will sooner or later mean logging into a Linux server over SSH anyway, WSL turns your own doorstep into the same language first.

    That is why we recommend doing command-line work on Linux or macOS, and the reasons are practical. Servers speak only the Linux dialect, so a laptop that speaks the same language means learning everything once. The vast majority of bioinformatics tools are developed and tested on Unix alone; installing them is one command there and often impossible on native Windows. There is also a historical reason: Unix was designed around small tools joined by pipes from the start, and the whole idea behind the efficiency in the next section is this family's invention.

    Why the terminal is still worth learning¶

    The reasons are practical. First, most of the lab's computing does not happen on your laptop: sequencing data is too big and alignment too slow, so the work runs on servers and clusters that have no desktop and no mouse, and what greets you after you log in over SSH is a shell. Second, most bioinformatics tools have no graphical interface at all, so using them means typing commands. Third, typing is where the efficiency comes from: the shell's idea is to chain small single-purpose tools with pipes, each one's output feeding the next, so "count how often each sequence occurs across a pile of FASTQ files and list the top ten" is one line of grep, sort and uniq, while opening those files in an editor stops being possible once they reach tens of gigabytes. Commands saved in a script can also be rerun anytime and handed to someone else exactly as they were.

    Two words people mix up constantly: the terminal is the window on your screen, and the shell is the program inside it that reads what you type and runs it, usually bash or zsh. Linux is the operating system nearly all of these machines run, which is why "learning Linux" and "learning the command line" are, for our purposes, the same thing.

    The arrival of coding agents has made all this more central, not less. Agents were trained on exactly this world of terminals and text streams, so the command line is where they are strongest, as the previous page describes. What becomes scarce is the ability to read commands rather than type them: knowing what rm -rf does before letting it run, and being able to tell whether the agent's one-liner answers the question you asked or some other question.

    Computing environments: laptop, server, cluster¶

    The lab's computing lives on three levels. The laptop is the workbench: writing code, looking at results, small jobs, all local. The server does the heavy work, with memory and storage orders of magnitude beyond a laptop and often a GPU or two; sequencing data lives on it directly, far too big to download anyway. The cluster is a crowd of servers, dozens or hundreds of machines that a scheduler hands jobs out to; you submit yours into the queue with sbatch and it runs when your turn comes.

    All three levels share one entrance: you log in over SSH and face a shell, and files move between them with command-line tools like scp and rsync. Installing software on the servers is not your job either; the lab manages environments centrally with pixi, see Routine Lab Support. This is why the command line comes first on this page: it is the common language of all these machines, learned once and spoken everywhere from laptop to cluster.

    Learning the shell¶

    The order that works, in our experience, is files first, streams second, remote machines third. Start with moving around and looking at things: ls, cd, cat, less, mkdir, cp, mv, rm. Then learn to think in streams: pipes, redirection, grep, wc, and a loop for the moment you catch yourself running the same command ten times. Only then go remote with ssh and scp, which is also when the cluster stops being an abstraction. That much is honestly enough for daily lab work; a script, meaning a string of commands saved in a file for the shell to run from top to bottom, will suggest itself once you are tired of retyping.

    For a first course we like Data Carpentry's shell-genomics: it teaches exactly these skills inside a genomics project, on real FASTQ files from an E. coli variant-calling dataset, so every command comes with a reason to care. It does expect the workshop's cloud setup, which takes some work to recreate on your own; if you'd rather start with zero preparation on your own laptop, pick Software Carpentry's shell-novice, which runs locally with a small download and takes an afternoon. Either way, keep 阮一峰's Bash 脚本教程 open on the side as the Chinese reference you look things up in. If lectures suit you better than guided workshops, MIT's Missing Semester compresses the same ground into a few dense sessions, good for a fast review pass once you have finished one of the courses. That is the whole reading list; depth can wait until a real problem asks for it.

    Knowing whether it stuck is its own step, and three free sites check you at increasing levels of realism. Linux Survival ends each short module with a quiz that asks you to type the right command, good for a ten-minute recall check. cmdchallenge gives you one puzzle per command in a browser terminal and verifies your answer automatically, no account needed. OverTheWire's Bandit is the capstone: you log into a real server over SSH and each level's password unlocks the next, so progress is proof. Levels 0 to 15 cover the basics on this page, and being able to do them without looking things up is a solid working definition of "I know the command line."

    One more suggestion, the fun kind. Hacknet is a story-driven hacking game, cheap on Steam and officially localized into Simplified Chinese, played entirely by typing into a terminal. Its everyday commands are real Unix, ls, cd, cat, rm, ps, kill, and the campaign doubles as a tutorial that introduces them one at a time. The hacking itself is simplified fantasy and there are no pipes or permissions, so what it teaches is comfort with the terminal rather than security skills. As a way to stop being afraid of the black window, it works surprisingly well.

    Git, the lab notebook for code¶

    Git is a version control system: it records the history of a folder as a series of commits, each one a snapshot with a message explaining why it exists. Once a project is in git, "I broke something and I don't know when" stops being scary, because every earlier state is one command away. Branches let you try an idea in a parallel draft without touching the working version. And for working with a coding agent, git is what makes delegation safe: every change the agent makes is a diff you can read and revert, which is exactly why the previous page insists on running agents inside git.

    The mental model worth building early is that your code exists in four places at once:

    flowchart LR
    A["<b>Working folder</b><br/><i>the files you edit</i>"] -- "git add" --> B["<b>Staging area</b><br/><i>the next snapshot being assembled</i>"]
    B -- "git commit" --> C["<b>Local repository</b><br/><i>the full history on your machine</i>"]
    C -- "git push" --> D["<b>Remote</b><br/><i>GitHub or Gitee</i>"]
    D -- "git pull" --> C

    Figure: the four places a change passes through. Most confusion with git is confusion about which of these you are looking at.

    For learning, two resources cover the basics. 廖雪峰的 Git 教程 is the standard Chinese first read: zero assumed background, command by command with screenshots, deliberately limited to the commands you actually need. Then Learn Git Branching, an interactive sandbox with an animated commit tree and a full Chinese interface. Branching and merging are where tutorials stop helping and intuition has to grow, and nothing grows it faster.

    Learn Git Branching doubles as the self-check: each level shows a target commit tree and only passes when yours matches the goal, so finishing the main and remote tracks means the skill is really there. To prove it transfers to the real thing, gitexercises.fracz.com gives you a local repository and grades your work server-side each time you run git verify. Those two passing you is a better signal than any amount of rereading.

    GitHub, and Gitee¶

    GitHub is where the remote in that diagram usually lives, but it earns its place for a different reason: it is where open science happens. Nearly every tool and dataset this roadmap mentions lives there as a public repository with its code, its issues, and its discussions attached, and reading a tool's repository is a research skill in itself. The two constructs to learn are the pull request, a proposal to merge your changes into another history with room for review, and the issue, a tracked thread for a bug or a plan.

    If you don't have accounts yet, go register on GitHub and Gitee first; the exercises below all happen in your own account. The fastest way in is GitHub's own Hello World, a ten-minute exercise done entirely in the browser, no installation, that walks through repository, branch, commit, and pull request. Then let GitHub Skills check you: its free courses run inside your own account and a bot reviews each step of your work automatically, so finishing the Introduction to GitHub course is itself the proof you can handle the workflow.

    From mainland China, GitHub is reachable but often slow, and Gitee, run by OSChina, is the domestic alternative worth knowing. It speaks exactly the same git, so clone, push, branches, and pull requests all work as you would expect, and a repository can have both as remotes: push to GitHub for the world, and to Gitee for fast access at home. The honest caveats: publishing a public repository on Gitee requires passing a content review, its Pages hosting service has shut down, and the global open-source community, meaning the tools and people you will actually collaborate with, is on GitHub. Learn git and GitHub as the real skill, and treat Gitee as a fast mirror rather than a replacement.

    One official tool is worth installing: the GitHub CLI (the gh command), which brings GitHub into the terminal, so cloning a repo, reading issues, opening a pull request, or checking CI status no longer needs a browser. Run gh auth login once after installing, and the point goes beyond saving yourself a few clicks: from then on a coding agent can run gh as you, and most git-plus-GitHub work, from creating repos and pushing code to opening PRs and answering issues, can be delegated to it while you watch the commands go by. Gitee has no official counterpart so far, but the heavy daily operations (clone, push, pull) are plain standard git anyway, so an agent can do those for you just the same; only platform features like issues and PRs need the browser.

    Tip

    Every tool mentioned on this page, from gh to Oh My Zsh and iTerm2 in Further reading, can be installed by simply telling your coding agent in plain language: "install this for me." Downloading, installing, and configuring are its job. That is exactly why the agent sits on the first page of this roadmap.

    Learning these with an agent beside you¶

    A coding agent changes the economics of everything on this page. It can write the find pipeline you half-remember, and it reads git's error messages better than most of us ever will. What it cannot do is know whether the command it just proposed is safe to run on data you cannot regenerate. So the skills worth sharpening are the supervisory ones: reading a diff before committing it, pausing at anything that deletes or overwrites, and insisting the agent work inside git so every step stays undoable.

    Two habits make the pairing work well. The first is to make the agent your tutor: when it runs a command you do not know, ask it to explain the command flag by flag, or paste it into explainshell. It is a patient teacher, and the explanation arrives attached to your actual problem. The second is to commit more often than feels necessary. With an agent editing at machine speed, the commit is the unit of undo, and small frequent commits are what let you say "that last idea was wrong" without losing the afternoon.

    Further reading¶

    • The Linux Command Line by William Shotts: the book-length version of the shell section, free as a PDF, with a community Chinese translation, 快乐的 Linux 命令行. For when a real problem starts asking for depth.
    • Pro Git: the official reference, free, in Chinese. The first three chapters cover daily life; the rest can wait.
    • 码农高天's 十分钟学会正确的 GitHub 工作流 (Chinese, bilibili): a professional programmer walks through the GitHub workflow open-source authors actually use to maintain code, in ten minutes.
    • Oh My Zsh: a configuration framework for zsh that gets you themes, better completion, and a pile of ready-made plugins; makes the terminal much nicer to live in.
    • iTerm2: the replacement terminal for macOS, much stronger on split panes, search, and shortcuts; on Windows the counterpart is Microsoft's own Windows Terminal.
    • Operating Systems: Crash Course Computer Science #18: thirteen minutes on why operating systems were invented at all, from batch processing and multitasking up to Unix. Episode 22 of the same series happens to be about command-line interfaces, and there is a Chinese-subtitled version on bilibili.
    • Warren Toomey's The Strange Birth and Long Life of Unix: an IEEE Spectrum long read on how a side project at Bell Labs became the foundation the industry stands on, and a good story.
